# 真实数据与论文基线运行指南

## 1. 当前可执行状态

无需 AMD 工具即可运行 `projects/build_all.ps1` 与 `projects/test_all.ps1`。它们覆盖五个独立工程、完整 MultiQueue、生产 HBM search/commit、VPR/FPGAIF 转换往返和强基线审计 runner。

本机已用 Vitis HLS 2022.2/Vivado XSIM 2022.2 完成五个 kernel top 的 csim、综合、Verilog RTL 协同仿真和 `.xo` 打包。可在 Linux 原生 ext4 工作区复现：

```bash
cd projects/persistroute
./run_hls.sh                   # 全部五个 top
./run_hls.sh search_hbm        # 也可单独选择一个 top
./run_vivado_ooc.sh            # production RTL 的 Vivado OOC 综合与报告
```

实测资源、时钟、协仿周期和 `.xo` SHA-256 保存在 `persistroute/experiments/hls_2022_2_u280.json`。Vivado OOC 综合的 DCP 哈希、时序、资源和 DRC 保存在 `persistroute/experiments/vivado_ooc_2022_2_u280.json`：4 ns 下 search WNS 为 +0.427 ns，commit WNS 为 -0.694 ns。该 OOC 记录早于本轮 AXI bundle 合并；当前 commit HLS 估算为 9.577 ns，仍未达到 250 MHz 目标。

OOC 结果不含 U280 shell/HBM controller、布局布线或最终时钟树，因此既不是 `v++` 系统实现后的时序/功耗结果，也不是上板证据。

本机已验证 XRT 2.14.354 与 U280 202211.1 XPFM，环境清单见 `persistroute/experiments/environment_2022_2_u280.json`。`v++ hw` 已完成 placement、routing、bitstream 和 xclbin 打包；在 180 MHz DATA clock 下最终 WNS 为 `+0.016 ns`、TNS 为 `0`，所有用户时序约束满足。阶段、报告路径和 xclbin SHA-256 见 `persistroute/experiments/vitis_link_2022_2_u280.json`。如需复现：

```bash
cd projects/persistroute
PERSISTROUTE_SKIP_HLS=1 ./build_xclbin.sh \
  /opt/xilinx/platforms/xilinx_u280_gen3x16_xdma_1_202211_1/xilinx_u280_gen3x16_xdma_1_202211_1.xpfm hw_emu
./build_xclbin.sh \
  /opt/xilinx/platforms/xilinx_u280_gen3x16_xdma_1_202211_1/xilinx_u280_gen3x16_xdma_1_202211_1.xpfm hw
```

`build_xclbin.sh` 默认将 Vivado 综合/实现限制为单路，以适应本机 16 GiB 内存；生产 search 综合单进程峰值 PSS 约 5.75 GiB，2 路在内核阶段仍会耗尽物理内存。更大内存机器可用 `PERSISTROUTE_SYNTH_JOBS` 和 `PERSISTROUTE_IMPL_JOBS` 覆盖。当前 VMware 虚拟机未透传 U280，`xbutil examine` 返回 0 devices，因此这些后续步骤完成前不得标记为“上板通过”或“论文结果”。

脚本将 `v++` 的临时文件、日志和报告分别隔离到 `build/xclbin/<target>/_x`、`logs` 和 `reports`，因此运行 `hw_emu` 不会覆盖已经归档的 `hw` 实现证据。

本机已进一步完成 XRT native host 的 `hw_emu` RTL 集成验证：4 search CU + 1 commit CU 的 xclbin 链接、XSim 启动与 host 事务均通过；固定 tiny production-ABI 输入的路径和最终 resource 状态与普通 C++ golden 逐字节一致。完整命令、hash、host 分段耗时和 XSim 日志见 `persistroute/experiments/hw_emu_2022_2_u280.json`。硬件仿真使用近似的全局存储器/互连模型，时间数据不能当作上板性能。

加速 PathFinder 控制层也已在真实 VTR 9 `diffeq` RR graph 子集上完成最终 RTL 验证。一个用例在单 wave 发射 4 个真实 connection，覆盖 4 个 Search CU 并发与 Commit；另一个用例首轮产生 1 个超用资源，第二轮完成 rip-up/re-route 并降为 0。两项 host 均返回 0、`legal=true`、`golden_match=true`，五类输出与 HBM C-model 逐字节一致。可审计输入、命令、逐轮哈希、输出 SHA-256、XSim 日志及结果限制见 `persistroute/experiments/accelerated_pathfinder_hw_emu_2026-08-26.json`。为控制 XSim 时间，终验使用完整 32920-node/344820-edge 图和经固定 task ID 选择的代表 connection 子集；不能将 `hw_emu` 墙钟时间解释为 U280 性能。

## 2. VPR 真实数据闭环

```powershell
# VPR 先生成固定 placement、route 与 XML rr_graph
vpr arch.xml design.blif --route_chan_width 200 `
  --route_file work\design.route --write_rr_graph work\rr_graph.xml

python persistroute\tools\vpr_route_connections.py `
  work\design.route work\connections.csv

python persistroute\tools\pack_hls_inputs.py `
  work\rr_graph.xml work\connections.csv work\vpr_input
```

生产 kernel 的节点/边/task 索引是 32 bit；每条 connection 的硬件路径长度是 16 bit。VPR `.route` 提取器将一个 net 的每个 SINK 转为 connection，并保留相同 `net_id` 以支持 route-tree trunk 共享。

无需 XRT 即可先在 Linux 上运行与 production ABI 相同的完整 PathFinder 控制层：

```bash
make -C persistroute/host persistroute_pathfinder
./persistroute/host/persistroute_pathfinder work/vpr_input work/routed
```

该入口执行多轮 present/history cost 更新、按过用 net rip-up 和多 sink route-tree 持久化，并生成
`work/routed.paths.csv`、`.route_trees.csv`、`.iterations.csv`、`.resources` 与 `.pathfinder.json`。
可用 `PERSISTROUTE_MAX_ITERATIONS`、`PERSISTROUTE_PRESENT_START_Q`、
`PERSISTROUTE_PRESENT_MULTIPLIER_Q`、`PERSISTROUTE_HISTORY_INCREMENT_Q` 冻结实验参数。
普通 C++ 入口仍是 correctness/control reference。其 HBM C-model backend 与 XRT 多 CU backend 已对真实 VPR RR graph 子集完成逐轮和逐文件 golden 对照；论文可据此声明 RTL 功能与多轮控制闭环通过，但不能用硬件仿真时间声称上板加速。批量 benchmark 统计和物理板性能仍需分别补齐后才可形成对应论文结论。

批量 CPU 基线现已冻结 4 个 VTR、2 个 Titan23 和 4 个 Koios 案例。运行记录要求 1-worker/16-worker 使用同一 TBB VPR 二进制并固定输入、seed、channel width 和 router options；十对 route 哈希、wirelength、CPD 与迭代数全部一致。执行 `python3 persistroute/tools/prepare_paper_artifacts.py` 会重新校验这些条件，并生成 `persistroute/paper/generated/` 下的 CSV、JSON、LaTeX 与 SVG；任何配对不一致都会失败退出。当前 whole-flow/route-stage 几何平均为 `1.046x/1.356x`，仅用于刻画 CPU 强基线，不是 PersistRoute 硬件加速比。

逐 connection timing criticality 已采用 host-side VPR/Tatum oracle 接入 CPU、HBM C-model 与 XRT 控制层：每轮路由后覆盖 VPR `net_delay`、运行真实 atom timing graph/约束的 STA，并将量化 setup criticality 反馈给下一轮 production `Task`。补丁、环境变量和命令见 `persistroute/README.md`；逐轮输入、VPR 日志、输出与摘要 CSV 都保留审计。该功能不会改变 32-byte ABI，也不要求重建 xclbin。当前已完成完整 `diffeq` CPU 与 HBM C-model 闭环；尚未把这一新增模式作为新的 RTL `hw_emu` 终验，且既有最终 `hw_emu` 不应因此重跑。

## 3. FPGAIF/RapidWright 商业器件闭环

本机已完成 FPGA24 v1.8 `logicnets_jscl` 的真实闭环。竞赛目标是 `xcvu3p`，不是 U280；官方 `benchmarks.tar.gz` 与 `xcvu3p.device` 均从 release v1.8 获取并记录 SHA-256。固定仓库提交为 `f86cb487...`，FPGA Interchange schema 为 `c985b464...`。官方 NXRoute 实测构建 8601776 nodes/37843442 edges、路由 39060 pins、写入 203287 PIPs；随后从结果抽取一条 6-PIP 完整信号网并回写原始 FPGAIF，Vivado 2022.2 报告该 net 为 `ROUTED`、0 conflict nets、0 routing-error nets。另从官方未布线 FPGAIF 重建无新增路由的输入 DCP，Vivado `route_design` 将 27961/27961 个 routable nets 全部布通，0 routing errors、0 DRC violations，wall time 66.34 s。官方输入没有用户时序约束，WNS/TNS/WHS/THS 均为 NA，因此该结果是合法布线基线而不是时序收敛结果。可审计记录见 `persistroute/experiments/fpga24_logicnets_jscl_2026-08-24.json`。

Linux bridge 的 FPGA24 非空回写命令为：

```bash
cd projects/persistroute
rapidwright/build.sh
rapidwright/run.sh extract work/routed.phys work/one_net.csv
rapidwright/run.sh apply work/unrouted.phys work/one_net.csv \
  work/one_net.dcp work/one_net.phys
```

`extract` 默认选择第一条非静态、非时钟、PIP 非空且 source 可达全部 sink 的网络；也可在最后追加精确 net 名。应再从输出 DCP 提取同一 net 并 `cmp` CSV，以验证回写的 PIP 集合逐字节可逆。RapidWright 生成的 DCP 在 Vivado 2022.2 中可能出现归档 checksum warning 12-8410；本次 DCP 仍成功恢复器件、网表、placement 与 routing，并完成 `report_route_status`。warning 必须保留披露，不能把它写成无警告。

从官方未布线输入运行 Vivado 全设计合法布线基线：

```bash
cd /home/gry/workspace/FPGA_Acc
source /tools/Xilinx/Vitis/2022.2/settings64.sh
source /opt/xilinx/xrt/setup.sh
exp=projects/persistroute/experiments/fpga24_logicnets_jscl_2026-08-24
projects/persistroute/rapidwright/run.sh apply \
  projects/persistroute/third_party/fpga24/logicnets_jscl/logicnets_jscl_unrouted.phys \
  "$exp/empty_routes.csv" "$exp/logicnets_jscl_vivado_input.dcp"
vivado -mode batch -nolog -nojournal \
  -source "$exp/run_vivado_full_route.tcl" \
  -tclargs "$exp/logicnets_jscl_vivado_input.dcp" "$exp/vivado_full_route"
```

必须同时检查 `route_status.rpt` 与 `drc.rpt`。本案例的
`timing_summary.rpt` 明确写有 `There are no user specified timing constraints.`，
不能将 `NA` 的 WNS/TNS/WHS/THS 解释为时序收敛。

CUFR 基线固定为官方仓库提交 `ea4b031...`、RapidWright
2023.2.1-beta、8 个本机可见 CPU、`-Xms1g -Xmx12g -Xss1g`。本次
`logicnets_jscl` 在 11 轮内将 overlap 降为 0，路由 wall time 26.33 s；
官方 `CheckPhysNetlist` 和 Vivado route status 通过，critical-path
wirelength 为 234，竞赛 score 为 47.097。作者仓库的 35.26 s/234/55.13
来自 2.90 GHz、768 GB 服务器，只可核对 QoR，不能直接计算跨机器加速比。
完整参数、哈希与日志见
`persistroute/experiments/cufr_logicnets_jscl_2026-08-24.json`。

RWRoute 基线固定为竞赛仓库 `f86cb487...` 与 RapidWright 子模块
`fc0f599...`。同一输入在 `-Xms1g -Xmx12g` 下 11 轮收敛，route-design
28.50 s、全进程 35.59 s，官方 checker 为 0 differences、27961/27961
fully routed、0 routing errors；critical-path wirelength 217，竞赛 score
53.731。该 12 GiB heap 仅证明 `logicnets_jscl` 成功，不能替代官方对全部
五个初始案例的至少 14 GiB heap 建议。证据见
`persistroute/experiments/rwroute_logicnets_jscl_2026-08-24.json`。

```bash

```

再将硬件路径变为具体 PIP 并回写：

```powershell

  work\rw_export work\rw_input.edge_catalog.csv work\routed.paths.csv work\routes.csv
persistroute\rapidwright\run.ps1 apply `
  design_placed.dcp work\routes.csv work\routed.dcp work\routed.phys
```

回写器拒绝未知 PIP、跨 net PIP 冲突和 source 无法到达全部 sink 的路由。最后仍必须以 Vivado `report_route_status`、`report_timing_summary`、`report_utilization`、`report_power` 作工业合法性和 QoR 验证。

## 4. 强基线

在 `experiments/strong_baselines/cases.example.json` 基础上建立真实 case 文件，设置 `VPR_BIN`、`RAPIDWRIGHT_BIN`、`VIVADO_BIN` 后运行：

```powershell
python experiments\strong_baselines\run_strong_baselines.py `
  --baseline vpr_serial --cases cases.json --output runs
python experiments\strong_baselines\run_strong_baselines.py `
  --baseline vpr_parallel --cases cases.json --output runs
python experiments\strong_baselines\run_strong_baselines.py `
  --baseline rwroute --cases cases.json --output runs
python experiments\strong_baselines\run_strong_baselines.py `
  --baseline vivado_route --cases cases.json --output runs
```

比较时固定 VPR channel width/seed、商业路由器使用同一 placed DCP，并同时报告转换、传输、全部重放、回写、Vivado 检查时间。Potter 等无法获得可运行代码的工作保持 B2 文献基线，不伪称复现。
