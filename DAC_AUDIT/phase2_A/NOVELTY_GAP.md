# Novelty gap and one bounded hypothesis

Existing pressure-prefix is a sparse integer prefix-sum implementation of the same L-shaped pressure sum. The off arm uses the historical per-edge reference. This is an exact engineering optimization; prefix sums, immutable snapshots, rollback, cache lookup and calling VPR are not independent research novelty. The controller already computes touched-net deltas and skips unaffected connections in `_cost_pair`; calling that existing code a new dependency algorithm would be inaccurate.

The strongest overlap is inside the baseline itself. Frozen VPR `vpr/src/place/place_timing_update.cpp:237` updates timing costs of connections whose criticality changed and preserves a consistent summation order. `update_timing_cost` selects incremental updates by default. VPR also exposes feedback recomputation and incremental timing controls in its [official CLI documentation](https://docs.verilogtorouting.org/en/latest/vpr/command_line_usage/#timing-driven-placer-options). Therefore “incremental timing-aware placement” is not a defensible novelty claim for TP without a narrower, experimentally distinguished method. This is a targeted overlap check, not an exhaustive literature novelty proof.

One potential hypothesis, contingent on the measured profile, is **reuse of exact transaction score terms across rejected proposals within a fixed native-feedback epoch, with dependency-checked invalidation**. It concerns repeated scoring across candidate histories, not merely summing a single L path faster. It is NOT implemented this round, and its novelty relative to existing incremental placement is unestablished.

The possible code locations are `TilePlaceV2Engine._cost_pair`, `_net_cost`, transaction proposal enumeration, `apply`/`restore`, `update_timing_feedback`, and the `pressure_q16` setter. The existing net cache has very high hit counts, so a second cache of the same quantities is unlikely to help. The potentially different reusable quantities are repeated candidate connection deltas, timing-edge incidence and bounding-box effects across a stable placement/dependency version. A read set must include the coordinates of all relevant net members (HPWL extrema), moved/swapped/macro members and occupied destination sites, pressure/timing feedback versions, criticality/focus state and any proposal-selection/no-good state that affects ordering. All members of a macro and both sides of a swap must be included.

A safe initial rule invalidates all score state on any native route/timing feedback replacement. Within one fixed feedback epoch, affected-net/connection state may be invalidated conservatively after commit or rollback, with version checks for all reads. A rejected trial's temporary feedback must not leak into restored state. Cache keys may not use only unchanged endpoints: pressure changes elsewhere on an L path, HPWL extrema from other members, shared routing capacity and timing criticality can change costs. Native routing/STA can change even when the local endpoints do not; native closure remains mandatory.

The reference is the frozen generic-parser CPU implementation with pressure-prefix enabled and no added reuse. A future minimal falsification test must compare every enumerated candidate's integer score and ordering, all submitted placement hashes, all decisions/feedback, final legality and QoR; it must include move, swap, macro, remote-pressure-change, remote-HPWL-extremum and feedback/rollback counterexamples. Track hit rate, lookup/invalidation overhead and complete outer process time. If reuse overhead cancels saved scoring time, or dependency checks cannot preserve exactness, reject this hypothesis. No parameter search or implementation of it is authorized by this report.

The frontier-suppression ablation's zero CPD effect remains negative evidence. A score-reuse hypothesis is about exact execution cost at the same search trajectory, so that quality-negative result does not directly refute it; it also supplies no positive speed evidence for it. Any meaningful paper would still require an additional distinction from ordinary incremental cost bookkeeping and equal-total-cost native baseline results.

Measured A proposal fractions in actual median runs are 70.47%, 56.66%, and 67.50%; pressure queries are 21.1M, 64.5M, and 53.9M. Existing net-cache hit rates exceed 99%, while index construction is milliseconds. These data motivate investigating candidate-contribution reuse rather than the already effective before-cost cache, but do not establish unique-key reuse or its net benefit. The decision is REVISE_ONE_HYPOTHESIS; detailed numbers and a bounded falsification proposal are in `PILOT_RESULTS.md` and `NEXT_GATE_DECISION.md`. No result here supports board speed, energy, all-P&R speedup or 3D generalization.

A concrete source observation narrows the hypothesis: `_cost_pair` repeatedly computes `_connection_congestion(source, sink, self.positions)` while forming each changed connection delta, although `_net_cost` caches the whole current-net aggregate. The aggregate does not supply individual connection contributions. Reusing those exact contribution terms across speculative move/swap/macro candidates is therefore a specific missing implementation capability, not a claim that the existing net cache is ineffective. Its reusable-key fraction and net cost remain unmeasured, and connection-level incremental caching alone is still not a novelty proof.
