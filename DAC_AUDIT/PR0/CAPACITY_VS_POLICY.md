# 容量与策略归因

**当前结论：容量边界机制已复现，旧 clma 失败主因仍 unknown；不能用旧 7.1093 倍支持新协议。**

历史证据在 `historical_attribution.json`，逐项保留本地原路径、SHA、大小及新哈希标记。只读了两臂的小型结果/轮次CSV，没有重跑旧30轮。完整读集臂共194299次搜索，30轮后12493/13458任务完成；轮次 failed 累计28945，最后一轮965个失败、overuse=0、exit=3。路径读集臂41467次搜索，8轮13458/13458完成、exit=0，轮次 failed 累计0。两者成功条件和经过的后续状态均不同。

| 历史失败类型 | 可确认程度 |
|---|---|
| 终态 | 到30轮上限仍缺965任务；零 overuse 不等于完整可行 |
| 16位完整读集计数 | 历史仓库 `fe9a8be^` 的 search 确有 `read_count==65535` 拒绝；但旧可执行文件SHA、逐调用trace缺失，实际贡献 unknown |
| 事务池／queue容量 | 原 host 有命令路径，缺对应完整环境/queue_depth/tx_capacity逐调用证据；贡献 unknown |
| 无路可达／hop界限／版本冲突 | 旧 status=3 或轮次 failed 不细分；不得将 unknown 填为 unreachable |
| 源码身份 | 两臂历史 executable/source commit 为 unknown；不以 b32、审计或本轮协议 commit 代替。b32 只是本轮新诊断源码 |

仓库前序完整读集源码与最终 tree-seed 还存在 seed 处理差异，所以本轮的65535 guard反事实是在**同一个b32搜索**上隔离记录上限，并非“恢复旧二进制后纠正容量”的完整复现。

小图数值见 `counterexamples/witnesses.csv`：65538节点图中完整动态依赖为65538（含路径 attachment），记录 guard=65535 的反事实失败，宽计数成功且目标成本102；相同搜索的窄路径计数在含 attachment 的65536项路径失败，宽计数成功；queue每bank深度1有明确 queue_capacity 失败。已知不连通二节点图为 exhausted_under_hop_bound，区别于上述容量失败。生产 status=3 未被改成“已知不可达”。宽参考内存有限、不可据此称可综合或FPGA容量已解决。
